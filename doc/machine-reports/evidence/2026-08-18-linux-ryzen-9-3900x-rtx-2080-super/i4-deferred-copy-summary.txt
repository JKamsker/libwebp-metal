Candidate and correctness correction
------------------------------------
The first candidate skipped the whole accepted-I4 publication loop. The loop
also publishes winning coefficient levels, so the end-to-end parity screen
caught changed hashes and byte counts:
  PNG baseline 743146796a9addc7 / 1610422 bytes
      candidate 244ef6f8a2e1645b / 1550038 bytes
  JPEG baseline 8abe9f8c33699452 / 1600198 bytes
       candidate 727442321fbf19a8 / 1529050 bytes

Those invalid timings were not used for a performance decision. The corrected
candidate always published the 256 coefficient levels and deferred only the
256 reconstructed luma pixels. It was compile-time restricted to
__CUDA_ARCH__ < 800. Method-5/6 trellis and the Ampere+ branch retained the
parent path. All seven focused CTests passed.

Corrected A/B protocol and result
---------------------------------
Each arm used a separate statically linked native-sm_75 executable. Two
order-reversed pairs per format used the six small/medium corpus images, one
warmup, and six measured persistent batches per process (48 JSON records):
  --variant cuda --mode lossy --batch-size 6 --method 4 --quality 75
  --warmups 1 --samples 6 --force-cuda <six PNG or JPEG inputs>

Pooled medians (milliseconds/image):
  PNG:  baseline 40.440180, candidate 40.360971, gain 0.079209
  JPEG: baseline 40.287371, candidate 40.330468, gain -0.043097

Every corrected PNG row used hash 743146796a9addc7 and 1610422 bytes. Every
corrected JPEG row used hash 8abe9f8c33699452 and 1600198 bytes. Baseline and
candidate CUDA resource reports were identical. The candidate was rejected
and removed because it was neutral-to-negative and far below the strict
1.5 ms/image retention threshold. No Ampere+ behavior or performance claim
was changed.
